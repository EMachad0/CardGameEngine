# Verified facts

- Parnas's criterion: "one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others." Decomposing by processing steps (a flowchart) is "almost always incorrect". Source: Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules", CACM 1972.
- Ousterhout: a deep module provides "powerful functionality yet [has] simple interfaces"; information leakage is "a design decision is reflected in multiple modules"; temporal decomposition, pass-through methods, classitis and 11 other red flags are "symptoms", not laws. Source: *A Philosophy of Software Design* 2nd ed., summary and CS190 lecture notes; full text in `research/00-scope/literature.md`.
- Evans: aggregates cluster entities and value objects, one root per aggregate, "allow external objects to hold references to the root only". A bounded context is a boundary "within which a particular model is defined and applicable". An anti-corruption layer provides the upstream system's functionality "in terms of your own domain model". Source: Evans, *DDD Reference* (2015).
- Vernon's aggregate rules: "Model True Invariants In Consistency Boundaries", "Design Small Aggregates", "Reference Other Aggregates By Identity", "Use Eventual Consistency Outside the Boundary". He calls them rules of thumb and lists reasons to break them. Source: Vernon, *Effective Aggregate Design* parts I to III (2011).
- Martin's package principles (CCP "Classes that change together are packaged together", ADP "no cycles", SDP, SAP, REP, CRP) are about binary deliverables, which in Rust means crates. The Dependency Rule: "source code dependencies can only point inwards". Source: butunclebob.com Principles of OOD; blog.cleancoder.com "The Clean Architecture" (2012).
- Cockburn: "A port identifies a purposeful conversation"; primary (driving) vs secondary (driven) is decided by "who triggers or is in charge of the conversation". Source: Cockburn, "Hexagonal Architecture" (2005).
- "Contract tests" (one abstract suite run against every implementation of an interface) is J.B. Rainsberger's term. Fowler's "ContractTest" is a different idea: checking that test doubles still match the real external service. Source: blog.thecodewhisperer.com "In brief: contract tests"; martinfowler.com/bliki/ContractTest.html.
- Simon Brown: if all types are public, packages are "simply an organisation mechanism... rather than being used for encapsulation". Source: simonbrown.je "Modular monolith" / *Clean Architecture* ch. 34.
- Catherine West's RustConf 2018 keynote endorses a "giant nested tree of entirely public structs" with systems as functions over `&mut game_state`. Her target is OO encapsulation, not one big state. Source: kyren.github.io/2018/09/14/rustconf-talk.html.
- Niko Matsakis lists four workarounds for a big struct whose methods borrow `&mut self`: inlining, factoring a sub-struct, free functions over fields, view structs. Source: smallcultfollowing.com "After NLL: Interprocedural conflicts" (2018).
- Inherent impls must be in the crate that defines the type; trait impls follow the orphan rule. Source: Rust Reference, Implementations.
- `unreachable_pub` flags `pub` items not reachable from other crates, and is allow-by-default. Source: rustc lint listing, allowed-by-default lints.
- Bevy 0.20.0 is the latest stable (2026-10-08). Buffered events are `Message`s (`MessageReader`/`MessageWriter`) since 0.17, and `Event` is for observers only. Source: crates.io; Bevy 0.16 to 0.17 migration guide.
- elevator-core keeps its simulation crate free of Bevy; one `Resource` holds the sim and one system steps it and writes its events as messages, "the only point where the core simulation and Bevy synchronize." Source: andymai.github.io/elevator-core, Bevy integration.
- Page-Jones defines two software elements A and B as connascent "if there is at least one change that could be made to A that would necessitate a change to B in order to preserve overall correctness." His rule: "Eliminate any unnecessary connascence and then minimize connascence across encapsulation boundaries by maximizing connascence within encapsulation boundaries." The 1992 paper names name, type, value, position, algorithm and meaning. Strength, degree, locality and the static/dynamic split come from Weirich and connascence.io, not from that paper. Source: Page-Jones, "Comparing Techniques by Means of Encapsulation and Connascence", CACM 35(9), 1992, pp. 148-149; connascence.io; full text in `research/01-coupling-and-hiding/sources.md`.
- Parnas on change: in the step decomposition a change to the line storage format "would result in changes in every module!", while in the second "Knowledge of the exact way that the lines are stored is entirely hidden from all but module 1." The first decomposition's interfaces "are the fairly complex formats and table organizations"; the second's "consist primarily in the function names and the numbers and types of the parameters." Source: Parnas 1972, pp. 1055-1056.
- Ousterhout: information can leak "even if it doesn't appear in a module's interface", as when two classes both know a file format; temporal decomposition splits read, modify and write into classes, and "Both the file reading and file writing steps have knowledge about the file format". An interface has formal parts (signatures) and informal parts ("overall behavior, side effects, constraints on usage"). Source: *A Philosophy of Software Design* 2nd ed. §4.1, §5.2, §5.3 via readers' notes (secondary); CS190 notes "Back-door leakage: not visible in the interface" (primary).
- Ousterhout's red flags: Vague Name, "broad enough to refer to many different things"; Hard to Pick Name, "a hint that the underlying object may not have a clean design." Source: *A Philosophy of Software Design* 2nd ed. §14.3 via readers' notes (secondary).
- Go blog: "Packages named util, common, or misc provide clients with no sense of what the package contains", and "If you cannot come up with a package name that's a meaningful prefix for the package's contents, the package abstraction boundary may be wrong." Cheney: "Name your packages after what they provide, not what they contain." matklad argues for one explicit catch-all module, given "a good solid design". Source: go.dev/blog/package-names (2015); dave.cheney.net (2019); matklad.github.io "Design Pattern: Kitchen Sink" (2021).
- Parnas 1972 has a section "Efficiency and Implementation": "If we are not careful the second decomposition will prove to be much less efficient than the first", because of "the repeated switching between modules". His conclusion: "we must abandon the assumption that a module is one or more subroutines." Source: Parnas 1972, ACM PDF; full text in `research/01a-hiding-and-depth/parnas-legacy.md`.
- Parnas extended the criterion himself: program families (IEEE TSE 1976), the "uses" relation (ICSE 1978, IEEE TSE 1979), and with Clements and Weiss a module guide where "system details that are likely to change independently should be the secrets of separate modules" (ICSE 1984, IEEE TSE 1985). That paper uses "secret" but may not have coined it. In 2002 he wrote "The principle is now clear. It is still hard to apply." Source: the papers and his Software Pioneers slides; `research/01a-hiding-and-depth/parnas-legacy.md`.
- Later authors build on Parnas 1972 and none found supersedes it. Ousterhout's CS190 notes: "More than 40 years old, but still one of the most important papers in all of systems." Martin's SRP post (2014) cites it and says SRP "seems to align with Parnas' formulation." Brooks's *Mythical Man-Month* (1995 ed.) has a section titled "Parnas Was Right, and I Was Wrong about Information Hiding". Sullivan et al. (ESEC/FSE 2001) re-analyzed KWIC with design structure matrices and option value, with results "consistent with Parnas's conclusions". Source: those texts; `research/01a-hiding-and-depth/parnas-legacy.md`.
- Critiques qualify the criterion: Kiczales et al. (ECOOP 1997) on aspects that "cross-cut the system's basic functionality"; Tarr et al. (ICSE 1999) name the "tyranny of the dominant decomposition", where a split chosen to limit some changes can lose "the ability to limit the impact of other changes". Source: the papers; `research/01a-hiding-and-depth/parnas-legacy.md`.
- A Rust struct pattern without `..` must name every field ("If `..` is not used, a struct pattern used to match a struct is required to specify all fields"), so a new field fails the build there with E0027; the same holds for enum struct variants. `#[non_exhaustive]` "has no effect" within the defining crate and forces `..` outside it. Source: Rust Reference, Patterns and Type system attributes.
- Clippy: `rest_pat_in_fully_bound_structs` (restriction) fires only when `..` is redundant; `unneeded_field_pattern` (restriction) flags `field: _` and works against exhaustive destructuring; `rest_pattern_accessible_field` (restriction), which enforces it, was merged in PR #15000 on 2026-07-11 and is not yet in a stable Clippy as far as checked. Source: rust-clippy source and PR #15000; `research/01a-hiding-and-depth/exhaustive-destructuring.md`.
- matklad: "it takes 10x more time to figure out *where* you should change the code"; ARCHITECTURE.md should "call-out architectural invariants", often "expressed as an *absence* of something". Source: matklad.github.io/2021/02/06/ARCHITECTURE.md.html.
- Ousterhout's module: "a module is any unit of code that has an interface and an implementation", including classes, functions, subsystems and services. The interface "consists of everything that a developer working in a different module must know in order to use the given module", with formal and informal parts (§4.2). Depth: "The benefit provided by a module is its functionality. The cost of a module (in terms of system complexity) is its interface." Source: *A Philosophy of Software Design* §4.1, §4.2, §4.4, via an unofficial 1st-edition full text; CS190 notes agree. `research/01b-depth-and-names/quotes.md`.
- Ousterhout: "it is more important for a module to have a simple interface than a simple implementation" (ch. 8). "the act of subdividing creates additional complexity", because of more interfaces, management code, separation and duplication; code is related when it shares information, is used together (both ways), overlaps conceptually, or can't be understood without the other (ch. 9). "length by itself is rarely a good reason for splitting up a method"; Conjoined Methods: "If you can't understand the implementation of one method without also understanding the implementation of another, that's a red flag" (§9.7 in 2e). Pass-through methods and "different layer, different abstraction" (ch. 7). Source: as above, unofficial full texts of both editions; `research/01b-depth-and-names/quotes.md`.
- Evans on modules: "Choose MODULES that tell the story of the system and contain a cohesive set of concepts." "Give the MODULES names that become part of the UBIQUITOUS LANGUAGE. MODULES and their names should reflect insight into the domain." The 2015 Reference adds "Modules are part of the model". The book's "The Pitfalls of Infrastructure-Driven Packaging" says technically driven packaging means "the code no longer reveals the model", and "keep all the code that implements a single conceptual object in the same MODULE, if not the same object." Source: Evans, *DDD Reference* (2015) p. 15, primary; *Domain-Driven Design* (2003) ch. 5 "Modules (a.k.a. Packages)", via a transcription (secondary).
- Cheney: "Name your packages after what they provide, not what they contain." The post is titled "Avoid package names like base, util, or common" and prefers some duplication to a shared util package. Clean Code ch. 2: "Avoid words like Manager, Processor, Data, or Info in the name of a class", with no reason given (secondary transcription). Source: dave.cheney.net (2019-01-08); Martin, *Clean Code* p. 25.
- Parnas 1972: "In this context "module" is considered to be a responsibility assignment rather than a subprogram." Source: Parnas 1972, p. 1054, primary PDF.
- Rust privacy: a private item "may be accessed by the current module and its descendants" (Reference). "Items in a parent module can't use the private items inside child modules, but items in child modules can use the items in their ancestor modules", and a `pub` struct's fields stay private (Book §7.3). So an `impl` in a child module reads the parent's private fields, and a parent can't read a child's. Source: Rust Reference, Visibility and privacy; The Rust Book §7.3.
