## Findings

### 1. "Parse, don't validate" (2019) — https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/
1. **Parsing vs validating:** "the difference between validation and parsing lies almost entirely in how information is preserved." Her definition of a parser: "a parser is just a function that consumes less-structured input and produces more-structured output." On `validateNonEmpty` vs `parseNonEmpty`: "`parseNonEmpty` gives the caller access to the information it learned, while `validateNonEmpty` just throws it away."
2. **Shotgun parsing:** she cites *The Seven Turrets of Babel: A Taxonomy of LangSec Errors and How to Expunge Them* (2016), http://langsec.org/papers/langsec-cwes-secdev2016.pdf. She quotes it: "Shotgun parsing is a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code—throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the 'bad' cases." She also quotes: "Late-discovered errors in an input stream will result in some portion of invalid input having been processed, with the consequence that program state is difficult to accurately predict." The paper's author names and venue are **[UNVERIFIED]**. I did not open the PDF.
3. **Strengthen the argument:** "Instead of weakening the return type, we can _strengthen_ the argument type, eliminating the possibility of `head` ever being called on an empty list in the first place." The comparison is `head :: [a] -> Maybe a` against `head :: NonEmpty a -> a`. She also writes: "you can think of a value of type `NonEmpty a` as being like a value of type `[a]`, plus a _proof_ that the list is non-empty."
4. **Make illegal states unrepresentable:** "**Use a data structure that makes illegal states unrepresentable.** Model your data using the most precise data structure you reasonably can." She does not credit the phrase. It is usually attributed to Yaron Minsky's "Effective ML" talk at Jane Street. The heading appears at https://blog.janestreet.com/effective-ml-revisited/, but the date it was coined is **[UNVERIFIED]**.
5. **Burden of proof:** "**Push the burden of proof upward as far as possible, but no further.** Get your data into the most precise representation you need as quickly as you can. Ideally, this should happen at the boundary of your system, before _any_ of the data is acted upon." Footnote 3 adds an exception for authorization before parsing.
6. **"Parse at the boundary before acting on the data"** is not a verbatim phrase. The closest sentences are: "they allow discharging checks on input up-front, right on the boundary between a program and the outside world" and "Doing that parsing up front, before acting on the data, can go a long way toward avoiding many classes of bugs."
7. **Practical advice list,** bold leads verbatim:
   - "Let your datatypes inform your code, don't let your code control your datatypes."
   - "Treat functions that return `m ()` with deep suspicion."
   - "Don't be afraid to parse data in multiple passes."
   - "Avoid denormalized representations of data, _especially_ if it's mutable." It continues: "Duplicating the same data in multiple places introduces a trivially representable illegal state: the places getting out of sync."
   - "Keep denormalized representations of data behind abstraction boundaries."
   - "Use abstract datatypes to make validators 'look like' parsers." This one uses "an abstract `newtype` with a smart constructor to 'fake' a parser from a validator."
   - Summary line: "write functions on the data representation you _wish_ you had, not the data representation you are given."

### 2. "Names are not type safety" (2020) — https://lexi-lambda.github.io/blog/2020/11/01/names-are-not-type-safety/
1. **Intrinsic vs extrinsic:** "the constructive modeling is _intrinsically_ type-safe; that is, the safety properties are enforced by the type declaration itself… its meaning is specified extrinsically via the `toOneToFive` smart constructor."
2. **Newtypes as tokens and trust boundaries.** King's term is "trust boundary", not "abstraction-based proof". She writes: "The primary safety benefit of newtypes is derived from abstraction boundaries… create a _trust boundary_ where internal invariants are enforced by restricting clients to a safe API." She is explicit that this is not a proof: "the newtype approach to type safety does not on its own constitute a _proof_ that a desired invariant holds. However, it restricts the 'surface area' where an invariant violation can occur to the defining module."
3. **The trade-off:** "This tradeoff may not seem all that bad, and indeed, it is often a very good one! Guaranteeing invariants using constructive data modeling can, in general, be quite difficult, which often makes it impractical." Her conclusion: "the churn of a production codebase tends to weaken encapsulation boundaries over time, so correctness by construction should be preferred whenever practical." The derived `Generic` and `Read` examples show how a smart constructor gets bypassed.

### 3. Proofs that go stale when state changes
1. **TOCTOU (CWE-367):** "The product checks the state of a resource before using that resource, but the resource's state can change between the check and the use in a way that invalidates the results of the check." https://cwe.mitre.org/data/definitions/367.html
2. **Gankra's "temporal validity"** (Alexis Beingessner, MSc thesis, Carleton, "© 2015"; DOI 10.22215/etd/2016-11260). In §6.3 "Hacking Generativity onto Rust": "we would have to deal with the problem of temporal validity. The indices into an array are only valid as long as the array's length doesn't change." The fix: "associate an array and its indices with a particular region of code. Unchecked indexing then simply requires that the input array and index are associated with the same region." The cost: "this trick is very delicate, and I don't expect it to see much use." https://raw.githubusercontent.com/Gankro/thesis/master/thesis.pdf
3. **GhostCell** (Yanovski, Dang, Jung, Dreyer, ICFP 2021, doi 10.1145/3473597). Branded types use "a static brand like 'id as a representative of some dynamic, stateful data structure". The guarantee is that "indices of brand 'id can only be used to access the vector with the exact same brand 'id". The authors trace the idea to Haskell's ST monad, which they say dates back "at least to the work of Launchbury and Peyton Jones [1995]". The paper states its own cost: "with GhostCell's coarse-grained permission tracking, it is not [possible to write different nodes concurrently]. Furthermore, the GhostCell API does not allow the user to mutate one GhostCell-wrapped node… while simultaneously holding interior pointers into other nodes." Paper: https://plv.mpi-sws.org/rustbelt/ghostcell/paper.pdf. Project page: https://plv.mpi-sws.org/rustbelt/ghostcell/
4. **A proof that borrows the state.** I found no single canonical name for this. It rests on Rust's "_aliasing XOR mutability_" rule (GhostCell abstract): while a `&T`-carrying proof is alive, the state cannot be mutated through safe code. The cost is that the proof can't outlive the borrow, so it can't be stored or held across mutation. That last sentence is my inference, not a quote.
5. **`generativity` crate:** "Create a trusted carrier with a new lifetime that is guaranteed to be unique among other trusted carriers." Its cost is invariance and macro-scoped brands: "non-invariant lifetimes _cannot_ be trusted." https://docs.rs/generativity/latest/generativity/
6. **`qcell` crate:** "Statically-checked alternatives to `RefCell` and `RwLock`." Its cost: "the restrictions are much stricter than they really need to be. For example it's not possible to borrow from more than a few different cells at the same time." https://docs.rs/qcell/latest/qcell/. The `ghost-cell` crate docs are **[UNVERIFIED]**. I did not open them.
7. **Typestate and consuming by value** (Cliffle, 2019). It "encodes information about an object's run-time _state_ in its compile-time _type_". It uses transitions that consume `self`: "We can't do _anything_ after sending the body, because the object is taken away from us." Its cost: since `self` "gets consumed and recreated at every step, it needs to be cheap", and loops get awkward. https://cliffle.com/blog/rust-typestate/. The original Strom & Yemini 1986 typestate paper is **[UNVERIFIED]**.
8. **Ghosts of Departed Proofs** (Noonan, Haskell Symposium 2018, which King cites). Its abstract says failure conditions "must be checked at the use-site, placing an unfair tax on the users who have ensured that the function's preconditions were correctly met." https://kataskeue.com/gdp.pdf

### 4. TypeScript and Python
1. **Zod `.brand()`** is a type-check-time construct only: "branded types do not affect the runtime result of `.parse`. It is a static-only construct." Brands exist because TypeScript is structural: "plain (unbranded) data structures are not assignable to the inferred type. You have to parse some data with the schema to get branded data." https://zod.dev/api?id=branded-types. Per a search snippet of https://zod.dev/basics, `.parse` "returns a strongly-typed deep clone of the input". I did not read that page in full.
2. **Python `NewType`** does nothing at runtime: "these checks are enforced only by the static type checker… `some_value is Derived(some_value)` is always true at runtime." https://docs.python.org/3/library/typing.html#newtype. By King's 2020 standard, `NewType` is a label only. It has no smart constructor and no runtime boundary.
3. **Pydantic** really does parse at runtime, but the result can go stale:
   - `validate_assignment` "Defaults to `False`… In case the user changes the data after the model is created, the model is _not_ revalidated."
   - `frozen` gives "faux-immutable" models and "Defaults to `False`." https://docs.pydantic.dev/latest/api/config/
   - `model_construct()` "does not do any validation, meaning it can create models which are invalid." https://docs.pydantic.dev/latest/concepts/models/

   This matches King's "trusted module" warning: these are escape hatches.

### 5. Critiques and limits
1. **King's own caveats:** "Consider the principles in this blog post ideals to strive for, not strict requirements to meet." She also writes: "It probably isn't worth breaking out singletons and refactoring your entire application just to get rid of a single `error "impossible"` call." Plus the newtype trade-off in section 2.
2. **Hillel Wayne, "Constructive vs Predicative Data"** (date **[UNVERIFIED]**), https://www.hillelwayne.com/post/constructive/. The constructive approach "is sound but not complete". It has ergonomic costs: "More code means more places to write bugs". It handles overlapping categories badly. It is weak on nonmonotonic properties: "Constructive systems are very bad at negating properties". Examples of such properties include "Arrays with a constrained sum." He also separates invalid from undesirable data: "sometimes data is in a valid but undesirable state."
3. **Practitioner misuse** (Vinay Raghu, https://www.vinayraghu.com/blog/the-problem-with-parse-dont-validate/). A parsed model had no loading state, so values that were not yet known came out as `false`. The fix was `Loading | Result | Error`. This is a modeling error, not a flaw in the principle. I list it as a weak source.
