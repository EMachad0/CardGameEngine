# Audit 4: the rules crate against the file-structure convention

## Summary

- `game` is one module by the doc's Rust rule (nine files, all `impl Game`), and it holds sixteen decisions that change independently.
- Four enums get their meaning from `_` filters or `matches!` predicates spread across `game`: `ModifierEffect`, `TriggerPattern`, `CardDefKind` and `PlayerInteractionState`. Adding a variant fails the build at none of those places.
- Several decisions are copied: the draft's fill order, the shape of card text in validation, damage marking, the characters in play, the order of play.
- Seven findings hide latent bugs no current card reaches. A temp copy of the crate reproduced four. No live bug found.
- 17 findings, 9 of high confidence. The roadmap names 3 and part of 4 more. 18 module or file names fail.

## Modules

I used the doc's Rust definition: a module is a `mod` whose private items hold the data of its decision. A child file that adds `impl Game` belongs to `game`. Files with no private data are listed as data: their layout is interface.

```
rules                 lib.rs: declarations and re-exports, no code
  action              data: Action, IllegalAction
  cards               mod.rs: declarations only
    binder            module: definitions by DefId, and what each card kind implies
    definition        module for DefId's representation only; CardDef, selectors, TriggerDef are data
    filter            data, plus fulfill_side_filter (the meaning of Side)
    loader            module: the card list, the DefId constants, the load-time validation rules
      static_card_definition   generated by def_ids!, DefId constants only
    modifier          module for the Modifiers list (a bare Vec); Modifier, ModifierEffect are data
    object            module: ObjectId allocation and order-of-play stamps (ObjectBag); Object is data
  choice              data, plus AmountBound's rule
  effect              data: the effect vocabulary, plus PendingEffect and ResolvingEffect (all fields pub)
  event               data
  game                module: everything in Game (game.rs, condition, lookup, player, resolve,
                      state_check, triggering, view, zone_move are one module)
  history             data (entries are pub)
  ids                 module: PlayerId as an index
  observer            module: Views hides Game from observers
  outcome             data
  rng                 module: SplitMix64
  trigger             data
  turn                module: seat rotation and turn count
  zones               module: the order inside Deck, Hand, Board, Graveyard
```

`game/player.rs` declares `Player` and `PlayerInteractionState` with `pub(super)` fields, so their data is visible to all of `game`. `game/view.rs` declares the public `View` types as data. Neither hides a decision from `game`.

Decisions held by `game`: setup (two players, shuffle, deal 3, hero def, player 0 first), turn start (mana +1 up to 10, refill, draw), mana payment, legality, the draft and its look-ahead search, the resolution loop, effect interpretation, selectors, filter matching, history recording and queries, derived stats and aura reach, trigger matching, the state check and outcome, zone moves and their order stamps, damage and fatigue, and visibility.

## Findings

### 1. `game` holds many independent decisions

- Decision: every decision listed under Modules for `game`.
- Places: game.rs:1-277, game/condition.rs, lookup.rs, resolve.rs, state_check.rs, triggering.rs, view.rs, zone_move.rs, player.rs. All in module `game`, about 1,700 lines.
- Evidence: each recent feature touched most of the nine files. ae79835 (triggers) touched 7, 995b2bb (resolution loop) 7, 8bcdccc (draft) 5. A change has to sort the module's code by decision first.
- Rule broken: "A boundary that holds many decisions that change independently doesn't. Its code has to be sorted by decision before a change." Also "Judge a parent by its own code, which should hold one decision, often how its children combine."
- Fix: move each decision that has its own data into a type declared in a child of `game`, with private fields: the draft (6), mana (14), history queries (13), resolution answers (8). `game` keeps the coordinator: `apply`, the loop, setup.
- Confidence: high.

### 2. Four `_` filters decide what each `ModifierEffect` means

- Decision: what each modifier kind does to an object.
- Places, all informal for "add a variant" (confirmed: a temp copy with `DebuffAtk` added passed `cargo clippy --all-targets -D warnings`):
  - game/lookup.rs:38-41, `ReduceManaCost` to cost. Module `game`.
  - game/lookup.rs:76-79, `BuffHealth` to health. Module `game`.
  - game/lookup.rs:102-105, `BuffAtk` to attack. Module `game`.
  - game/lookup.rs:130-136, `GrantTrigger` to triggers. Module `game`.
- Rule broken: "When several filters together decide what each variant means, give that decision one exhaustive match."
- Fix: one exhaustive match over `ModifierEffect` that sorts each modifier into its stat, called by the four lookups.
- Confidence: high. Bug: none today. Roadmap names the change (signed modifiers), not this finding.

### 3. Trigger matching ends in a catch-all

- Decision: which event each `TriggerPattern` matches.
- Places: game/triggering.rs:46-61, whose last arm `(_, _)` returns `false`. Module `game`. Informal for "add a pattern": confirmed with a temp copy where `TriggerPattern::Entered` built clean and would never fire. game/lookup.rs:115 is a filter that only wants `Died(Itself)`, which the doc allows.
- Rule broken: "An exhaustive `match` with no `_` arm, so adding a variant fails the build at every place that has to handle it. This is for matches that decide something for every variant."
- Fix: match `pattern` exhaustively, and test the event inside each arm with `matches!` or `if let`.
- Confidence: high. Bug: none today. Roadmap names the change (enter effects), not this finding.

### 4. The meaning of each card kind is spread over `is_*` filters

- Decision: what a `CardDefKind` implies: which zone it plays to, whether it is a character, whether it has health on the board, whether auras reach it, whether it leaves play on death, which kind filters match it.
- Places:
  - cards/binder.rs:34-48, 62-76, 86-100: exhaustive matches. Formal. Module `cards::binder`.
  - cards/binder.rs:50-60: `is_spell`, `is_minion`, `is_hero` via `matches!`. These feed the informal places below.
  - game/lookup.rs:56-63: in play means hero in the hero zone or minion on the board. Informal. Module `game`.
  - game/lookup.rs:158: auras reach minions only. Informal. Module `game`.
  - game/zone_move.rs:106-110: heroes are not removed on death. Informal. Module `game`.
  - game/condition.rs:90-105 with cards/filter.rs:5-22: `CharacterKindFilter` and `CardKindFilter` repeat the kind list and map it with `contains` chains. Informal. Modules `game` and `cards`.
  - game/resolve.rs:304, 316: history counts by kind. Informal. Module `game`.
  - cards/loader.rs:653-657, 684-688: only minions carry auras, for validation. Informal. Module `cards::loader`.
- Evidence: a temp copy with a new `CardDefKind::Location` failed the build only at the six matches in binder.rs. When 5273105 added `Hero`, lookup.rs, state_check.rs and zone_move.rs were edited by hand.
- Rule broken: "When several filters together decide what each variant means, give that decision one exhaustive match." Also "Give each question its own function, even when two share an answer today."
- Fix: give `Binder` one function per question (`is_character`, `receives_auras`, `leaves_play_on_death`, `matches_kind_filter`), each an exhaustive match, and make the places above ask them.
- Confidence: high. Bug: none today. A board kind that is not a minion would compile and panic at game/state_check.rs:13-15 (by reading).

### 5. `AmountBound::is_satisfied` answers two questions

- Decision: when a choice may stop and when it is full.
- Places:
  - choice.rs:23-27 `is_satisfied`; choice.rs:29-33 `upper_bound`, which nothing calls. Data module `choice`.
  - game/condition.rs:35-45 wraps it as `check_choice_count_fulfilled`. Module `game`.
  - Used as "full, offer no more candidates": game.rs:168-174, game/condition.rs:23-25. Used as "may stop, offer Play": game.rs:190-194, game/condition.rs:118-122. Module `game`. Informal for "add `AtMost`".
- Rule broken: "Give each question its own function, even when two share an answer today. The second can be built on the first. The day their answers differ, each changes alone."
- Fix: two functions, `may_stop` and `is_full` (built on `upper_bound`). Offer candidates while not full, and `Play` once every choice may stop.
- Confidence: high. Latent bug, no current card has `AtMost`. Confirmed with a temp copy: Ping with `AtMost`, a Recruit on the board, after `Draft` the legal actions were only `Play` and `Cancel`. Roadmap names it ("His first AtMost counted as filled before any choice").

### 6. The draft's layout and fill order are known in five places

- Decision: how a draft stores its choices, and that `Choose` fills the first open choice in declaration order (ADR 0010).
- Places, all in module `game`. The layout is a type, so formal for a layout change. The fill order and the per-choice count are copies, informal for every change:
  - game/player.rs:20-23: the layout, `Vec<(ObjectId, ChoiceId)>`.
  - game.rs:163-189: first open choice; per-choice count at 164-167.
  - game/condition.rs:107-137: the same first-open loop in the look-ahead; count at 114-117.
  - game/condition.rs:18-22: the per-choice filter again.
  - game/resolve.rs:84-95: groups the pairs by choice id at `Play`.
  - game/view.rs:165-178: drops the choice ids for `DraftView`.
- Rule broken: "A step hands its output forward as data, so every later step knows that data's layout." Also "Make a decision its own module when its knowledge sits in more than one place, today or in planned work".
- Fix: a `Draft` type in a child of `game` with private targets, and `open_choice`, `chosen_for`, `push`, `into_targets`. `legal_actions` and the look-ahead ask it.
- Confidence: high. Bug: none. Roadmap names the changes (`Back`, `AtMost`, 06c), not this finding.

### 7. Validation copies the shape of card text, with gaps

- Decision: where effect sequences can sit in a card definition, and which of them resolve without a draft.
- Places:
  - cards/loader.rs:614-624: walks `play_effects` only. Module `cards::loader`. Informal.
  - cards/loader.rs:645-676: walks `triggers` and minion aura `GrantTrigger`s. Informal.
  - cards/loader.rs:678-698: walks `play_effects`, `triggers`, minion aura `GrantTrigger`s. Informal.
  - game/lookup.rs:119-142: at runtime, triggers come from the definition and from any `GrantTrigger` modifier, including `CardDef.modifier_effects` (cards/definition.rs:29) and those given by `Effect::Buff` and `Effect::AddFriendlyAura` (effect.rs:31-38). Module `game`.
- Gaps: no walker visits `modifier_effects` or a `GrantTrigger` inside `Buff` or `AddFriendlyAura`.
- Rule broken: "A step that checks what a later step will do has to know that step's rule." Also "One place knows each decision".
- Fix: one walker in `cards::definition` that yields every effect sequence in a definition, nested ones included, marked "resolves with a draft" or not. Each validation rule asks it. 06b's nesting then changes one function.
- Confidence: high. Latent bug, no current card has a `GrantTrigger` there. Confirmed with temp unit tests: a `modifier_effects` trigger that reveals and never resolves passes `validate`, and so does a `Buff` granting a trigger with a `Chosen` selector. A minion holding that granted trigger, added the way `Buff` adds it (game/resolve.rs:198-202), panicked at game/resolve.rs:366, "Choice not fulfilled", when it died. Roadmap: no.

### 8. Resolution answers live on `Object`

- Decision: where choice targets and pick answers are kept, and how long.
- Places, all informal for "move the answers" or "clear them":
  - cards/object.rs:20-21: `choice_targets`, `pick_targets` as pub fields. Module `cards::object`, which hands out `&mut Object`.
  - game/resolve.rs:84-95 writes choice targets at `Play`; game/resolve.rs:360-368 reads them. Module `game`.
  - game/zone_move.rs:202-207 writes a pick answer; game/resolve.rs:171-186 reads the first match. Module `game`.
- Rule broken: "A decision whose data crosses the boundary isn't hidden, because any caller can copy it."
- Fix: keep answers in the resolving effect's context (ADR 0015), behind `record_pick`, `picked(pick_id)` and `chosen(choice_id)`. `Object` loses both fields.
- Confidence: medium (the home is 06b's call). Latent bug. Confirmed with a temp copy where Drillmaster's trigger reveals 1 and resolves pick 0: after two spells the hand held the first pick twice, and the second revealed card was in no zone. Roadmap names it.

### 9. `Died(Itself)` has two paths and a relied-on order

- Decision: when an object's own death triggers fire.
- Places, all in module `game`:
  - game/lookup.rs:112-117 and game/zone_move.rs:96-103: `kill` queues them before removal.
  - game/zone_move.rs:105-112: removes non-heroes, then emits `Died`. The order is what keeps the matcher from firing them again.
  - game/triggering.rs:47-49, 107-108: the matcher also fires `Died(Itself)` for any listener still in `board_characters`.
  - game.rs:216-227: heroes are always in `board_characters`.
- Knowledge: informal for "a dying object that stays in play", such as a hero.
- Rule broken: coupling through "a relied-on meaning and a required call order", and "One place knows each decision".
- Fix: one place decides it. Either the matcher's `Died` arm skips `Itself` and `kill` owns it, or the matcher is the only path and excludes the dead by state rather than by removal order.
- Confidence: medium. Latent bug. Confirmed with a temp copy whose hero has a `Died(Itself)` trigger: one hero death queued two entries. Roadmap names the cause in part (dead heroes stay in `board_characters`).

### 10. The characters in play are computed four ways

- Decision: which objects are characters in play, and in what order.
- Places, all in module `game`, informal for every change:
  - game.rs:216-227 `board_characters`: heroes and boards, sorted by order stamp, dead heroes kept.
  - game/condition.rs:47-67 `scan_characters_with_filter`: heroes, then boards, in seat order, dead heroes kept.
  - game/state_check.rs:9-36: board minions, plus heroes of players still `playing`.
  - game/lookup.rs:56-63 and 89-92: in-play checks for health and attack.
- Rule broken: "One place knows each decision. ... Ideally one place knows it, and every other place asks it".
- Fix: one `characters_in_play` question that the filters, `emit` and the state check ask. Order is a separate question (11).
- Confidence: medium. Latent bug: with three players, an eliminated player's hero is still a candidate for Wild Bolt's random pick and for Blast. Unreachable, because `Game::new` takes two decks. Confirmed by reading. Roadmap names it in part (dead heroes, N-player).

### 15. `loader` holds three decisions, and storing skips validation

## Names

Judged against siblings and the glossary. Each failing name comes with a real function that shows it.

1. `game`: doesn't rule out its siblings. `Game::history_query` (game/resolve.rs:285) counts history, but sits under `game`, not `history`. `Game::fulfill_trigger_pattern` (game/triggering.rs:39) belongs to `trigger` by name.
2. `game/lookup`: not a glossary term, and every read fits. `Game::mana` (game.rs:229) and `Game::players` (game.rs:274) are lookups in game.rs. `Game::playing` (lookup.rs:213) is in lookup.rs.
3. `game/condition`: every boolean fits. `Game::is_pending_interaction` (resolve.rs:269) and `fulfill_side_filter` (cards/filter.rs:45) are conditions elsewhere. The file holds filter matching and the draft look-ahead.
4. `game/resolve`: glossary "Resolve" is carrying out a card's text. `Game::history_query` (resolve.rs:285) is a read used by cost. `apply_action` handles `EndTurn` and `Cancel`, which resolve nothing.
5. `game/zone_move`: `Game::damage` (zone_move.rs:262) moves nothing. `Game::pick` (zone_move.rs:181) records an answer.
6. `game/triggering`: `Game::history_from_event` (triggering.rs:64) and `emit` aren't about triggers. `Game::triggers` (lookup.rs:119) and `death_rattles` (lookup.rs:112) are, and live in lookup.
7. `trigger`: doesn't exclude `game/triggering`. `TriggerDef` sits in cards/definition.rs:85, and `fulfill_trigger_pattern` in game.
8. `cards`: card text is split between `cards/` and the root. `AmountBound::is_satisfied` (choice.rs:23) and `EffectSequence::as_slice` (effect.rs:54) belong to cards by name.
9. `cards/definition`: every piece of card text fits. `PlayerSelectorFilter::all` (definition.rs:96) is a selector, which the glossary puts in an effect, beside its sibling `CharacterFilter::all` in filter.rs.
10. `cards/filter`: `Game::fulfill_card_filter` (condition.rs:80) evaluates a filter in game. `PlayerSelectorFilter` is in definition.rs, `PlayerFilter` and `TurnFilter` in history.rs.
11. `cards/loader`: `validate_pick_order` (loader.rs:700) is a rule about effect order, not loading. The file also holds the card list and the IDs.
12. `static_card_definition`: holds `DefId` constants only. `CardDefLoader::load_all` (loader.rs:94) returns the static definitions and sits outside it.
13. `cards/modifier`: not a glossary term; the glossary has Buff and Aura. `Game::modifiers` (lookup.rs:144) and `Game::friendly_aura` (lookup.rs:183) compute modifiers in game.
14. `choice`: `EffectAmount::from` (choice.rs:10) serves every verb. `PickId` and `PickTarget` are Pick, which the glossary flags against Choose. The roadmap names `EffectAmount`.
15. `effect`: holds the card-text vocabulary and the resolution cursor. `ResolvingEffect::advance` (effect.rs:104) fits `game/resolve` too. `Game::effect_amount` (resolve.rs:278) fits `effect` and lives in resolve.rs.
16. `ids`: holds only `PlayerId`. `ObjectBag::next_id` (object.rs:34) and `DefId::new` (definition.rs:18) make IDs elsewhere.
17. `turn`: holds seat order and turn count. `Game::start_turn` (game.rs:254), with the mana refill and draw, fits "turn" and lives in game.rs.
18. `game/player`: nearly every `Game` function takes a player. `Game::mana` (game.rs:229) and `Game::playing` (lookup.rs:213) read only `Player` and live elsewhere. Low confidence.

Passing: `action`, `event`, `outcome`, `history`, `observer`, `rng`, `zones`, `cards/binder`, `cards/object`, `game/state_check`, `game/view`.

## Already following the rules

- Private fields hide a representation: `PlayerId`, `Rng`, `TurnOrder`, `Deck`, `Hand`, `Board`, `Graveyard`, `ObjectBag`, `Binder`, `Views`.
- Private constructors: only `ObjectBag` makes an `ObjectId`, and only `cards` makes a `DefId`.
- Clippy bans make three decisions formal: no `HashMap` or `HashSet`, no clock, and only `Game::emit` calls `Observer::event`.
- Exhaustive matches where a decision covers every variant: `Action` (resolve.rs:62), `Effect` (resolve.rs:147, loader.rs:627, 703), both selectors (resolve.rs:334, 350), `EffectAmount` (resolve.rs:279), `ZoneMove` (zone_move.rs:16), `TriggerSubject` (triggering.rs:107), `PlayerInteractionState` in `legal_actions` (game.rs:116), the six kind matches in binder.rs.
- One command takes legality away from callers: `apply` checks `legal_actions` and then runs (resolve.rs:45).
- One `emit` records history, reports and matches triggers (triggering.rs:10-21).

## Doc feedback

1. "A module in the general sense is a `mod` whose private items include the data its decision is stored in." Eight files hold no private data (`action`, `choice`, `effect`, `event`, `history`, `outcome`, `trigger`, `cards/filter`). The doc doesn't say whether the other rules apply to them. I treated their layout as interface and judged their names anyway.
2. "child files that add `impl` blocks to their parent's type are part of the parent's module." Then `game`'s nine files are one module. "Don't split by processing step" speaks of "one decision lands in several modules", so a step split across files of one module isn't covered. Nor does the doc say whether those files are siblings for the names rule. I judged them as siblings and used "One place knows each decision" for copies between them.
3. "Informal knowledge is acceptable where its locality is high, meaning its places sit close together in code that serves the same decision." In a module that holds many decisions, "code that serves the same decision" is what's missing. The doc doesn't say whether two files of one module count as close. That decided whether findings 6 and 14 are findings.
4. That sentence pulls against "Prefer taking knowledge away from callers to making it formal. A caller that must call two functions in order still knows the decision." The five `update_order` calls in zone_move.rs sit together, so the first allows them. Every move function must still remember the stamp, and the planned zone reset too, which the second rejects. I didn't list it.
5. "A name passes when a reader, given any function, existing or new, can tell from the name alone whether it belongs." `legal_actions` fits `action`, `emit` fits `event`, `decide_outcome` fits `outcome`. They must live in `game`, because they read its private state. The doc doesn't say whether that fails the data module's name. I passed those names and failed the files that hold the functions.
6. "Judge a name against its siblings, the other names a reader picks between at the same level." Readers pick between `trigger` and `game/triggering`, and between `zones` and `game/zone_move`, at different levels. The rule misses these pairs.
7. "Judge whether a decision is likely to change by reasoning about the domain: what other systems in it already vary, what the roadmap plans". Mana rules vary in every Hearthstone game, but the roadmap is silent. The doc gives no weight between the sources, so finding 14's confidence is my call.
8. "This is for matches that decide something for every variant." `fulfill_trigger_pattern` matches a pair (pattern, event). It decides for every pattern and filters events. The doc doesn't say which side of a tuple match must be exhaustive.
9. "When several filters together decide what each variant means, give that decision one exhaustive match." The kind filters map one enum to another with `EnumSet::contains` chains and no match at all (condition.rs:90-105). The doc's tools name only match arms. I applied the rule by analogy.
10. `static_card_definition` is declared by a macro inside loader.rs and used as `crate::static_card_definition` through `pub use`. The doc doesn't say at which level its name is judged. I judged it inside `cards::loader`.
11. "an interface of questions and commands can replace that knowledge while asking callers to know less than the data would." A `History` query needs the game's turn, active player and card kinds as arguments. The doc doesn't say whether an interface that takes context still asks callers to know less. I said yes.
12. "a decision hides from the parent only in a type declared in a child." Several of `game`'s decisions have no data of their own: legality, trigger matching, the state check. They read all of `Game`. The doc doesn't say where such a decision goes when its parent holds too many, so finding 1's fix covers only decisions that own data.
