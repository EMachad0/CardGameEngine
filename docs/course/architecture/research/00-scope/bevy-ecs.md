# Bevy and ECS code organization

Researcher report, session 00. Kept in full.

## Summary
Current stable Bevy is **0.20.0** (crates.io, published 2026-10-08), not 0.17; 0.18, 0.19 and 0.20 have shipped since. The 0.17 split (buffered `Message` with `MessageReader`/`MessageWriter`; `Event` only for observers) still holds, with further renames since: `Replace` lifecycle event became `Discard` (0.19), resources are now stored as components (0.19), and `On<Add, B>` became `On<Add<B>>` (0.20). Sources agree on one plugin per feature, a thin `main.rs`, and explicit ordering via sets and states. For a pure rules core, the clearest pattern found is elevator-core: a core crate with no Bevy dependency, one resource holding the sim, and a single bridge system that steps it and re-emits its events as `Message`s.

## Findings

**1. Version and API names**
1. **0.20.0 is latest stable**: crates.io `max_stable_version` = 0.20.0; 0.18 released 2026-01-13, 0.19 2026-06-19, 0.20 2026-10-08. [crates.io API](https://crates.io/api/v1/crates/bevy), [Bevy news](https://bevy.org/news/)
2. **Message vs Event (0.17, still current)**: "`EventWriter`, `EventReader`, and `Events<E>`, are now known as `MessageWriter`, `MessageReader`, and `Messages<M>`"; "Event … (and the `Event` trait) are now used solely for 'observable events'". `send_event` became `write_message`; `RemovedComponents::events` became `::messages`. [0.16→0.17](https://bevy.org/learn/migration-guides/0-16-to-0-17/). Current docs: messages "are evaluated at fixed points in the schedule rather than immediately… This allows for more predictable scheduling", and are "more efficient than `Event`s" for batches. [Message docs](https://docs.rs/bevy/latest/bevy/ecs/message/trait.Message.html)
3. **Observer renames**: 0.17 `Trigger` became `On`, `OnAdd` etc. became `Add`/`Insert`/…; `trigger_targets` removed for `#[derive(EntityEvent)]` with an `entity` field; the `Condition` trait became `SystemCondition`; system sets moved to a `*Systems` naming convention ([0.16→0.17](https://bevy.org/learn/migration-guides/0-16-to-0-17/)). 0.19: "`Replace` has been renamed to `Discard` and `ComponentHooks::on_replace` … to `ComponentHooks::on_discard`" ([0.18→0.19](https://bevy.org/learn/migration-guides/0-18-to-0-19/)). 0.20: "`On<Add, A>`" became "`On<Add<A>>`", with the `B: Bundle` generic moved into lifecycle events ([0.19→0.20](https://bevy.org/learn/migration-guides/0-19-to-0-20/)).
4. **Resources are components (0.19)**: "resources are now stored as components on singleton entities"; a type can no longer derive both `Component` and `Resource`; "non-send resources" renamed "non-send data". [0.19 news](https://bevy.org/news/bevy-0-19/), [0.18→0.19](https://bevy.org/learn/migration-guides/0-18-to-0-19/)
5. **Required components and hooks (0.20 docs)**: "when `A` is inserted, `B` will *also* be initialized and inserted", recursively. Hooks: `on_add`, `on_insert`, `on_discard`, `on_remove`, `on_despawn`. Storage: "Table storage… optimized for query iteration"; "SparseSet… optimized for component insertion and removal". [Component docs](https://docs.rs/bevy/latest/bevy/ecs/component/trait.Component.html)
6. **Bundles vs BSN (0.19)**: bundle functions are "the 'old' approach to spawning"; `bsn!` introduced; no deprecation of `Bundle` found; "we aren't yet shipping a first-party `.bsn` asset loader." [0.19 news](https://bevy.org/news/bevy-0-19/)
7. **Plugins, systems, schedules**: bevy_ecs README: "Systems are normal Rust functions"; "Schedules run a set of Systems according to some execution strategy"; bevy_ecs "can easily be used as a standalone crate". [bevy_ecs README](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md)

**2. Project structure**
1. **bevy_new_2d** (Bevy Jam working group): function plugins `pub(super) fn plugin(app: &mut App)`. "Everything that belongs to the `player` is only in `player.rs`… always have one plugin per file." `Screen` state enum with `DespawnOnExit`, `impl Bundle` functions, asset-preloading resources, feature-gated `dev_tools` plugin. [design.md](https://github.com/TheBevyFlock/bevy_new_2d/blob/main/docs/design.md)
2. **Tainted Coders**: quotes the Exofactory developer: "No plugin should import anything from any other plugin ever." "Start with one crate"; keep `main.rs` thin; put the game in a `lib.rs` `GamePlugin` so tests can run with `MinimalPlugins`. [Code Organization](https://taintedcoders.com/bevy/code-organization)
3. **Cheat Book**: now says "This entire book is outdated and no longer maintained" (targets 0.14). Suggests plugins "for different states" and "for various sub-systems". [Plugins](https://bevy-cheatbook.github.io/programming/plugins.html)
4. **bevy_best_practices** (tbillington): "All systems added to the `Update` schedule should be bound by run conditions on `State` and `SystemSet`"; co-locate `OnEnter`/`OnExit` registration; "Prefer Events for structuring logic" (code still uses pre-0.17 `EventReader`). [README](https://github.com/tbillington/bevy_best_practices)
5. **Bevy's own repo**: the 0.17 reorganization moved types out of `bevy_render` into `bevy_camera`, `bevy_light`, `bevy_mesh`, `bevy_shader` and others "to improve modularity, code organization and compile times." [0.16→0.17](https://bevy.org/learn/migration-guides/0-16-to-0-17/)

**3. Component granularity**
1. **For small components**: "It's friendlier to the cache… run more of our systems in parallel… finer grained change detection"; caveat: "we also make certain queries harder". [Tainted Coders](https://taintedcoders.com/bevy/patterns/small-components)
2. **Against**: LogLog Games is "very much on the *hard disagree* side in complete generality, unless maximum performance is of concern." [LogLog](https://loglog.games/blog/leaving-rust-gamedev/)
3. **Archetype costs**: "adding/removing table components… requires copying the data of all table components" ([Cheat Book storage](https://bevy-cheatbook.github.io/patterns/component-storage.html), written for 0.9, outdated). SparseSet "lets an entity gain or lose that component without moving its table components"; archetypes "are never destroyed" ([Tainted Coders archetypes](https://taintedcoders.com/bevy/archetypes)).
4. **Bevy splits its own giant components**: "`Window` has become a very large component… we have split it into multiple components"; `Hdr` became a separate marker component. [0.16→0.17](https://bevy.org/learn/migration-guides/0-16-to-0-17/)

**4. Ownership of writes**
1. **Immutable components** (0.16, still in 0.20 docs): "The only way to modify an immutable component is to insert a new instance on top… hooks and observers… capture *every* change"; "a niche tool". [0.16 news](https://bevy.org/news/bevy-0-16/)
2. **Private fields**: a private `QuestId(u32)` plus generator "means quest ids can only be generated in one place". [bevy_best_practices](https://github.com/tbillington/bevy_best_practices)
3. **Explicit ordering**: "Event readers should be ordered after their respective writers" ([bevy_best_practices](https://github.com/tbillington/bevy_best_practices)). Bevy's `ambiguity_detection` reports "systems with conflicting access but indeterminate order"; off by default (`LogLevel::Ignore`). [ScheduleBuildSettings](https://docs.rs/bevy/latest/bevy/ecs/schedule/struct.ScheduleBuildSettings.html)
4. **Unverified**: no official Bevy guidance found that names a "single writer per component" rule; the pattern appears only implicitly through the tools above.

**5. Rules core outside Bevy**
1. **elevator-core** (strongest example): "nothing in `elevator-core` itself depends on Bevy"; `step()` has "no I/O, no wall-clock dependency"; determinism: "same config + same sequence of inputs produce identical event streams" ([Headless](https://andymai.github.io/elevator-core/headless-non-bevy.html)). Bridge: `#[derive(Resource)] SimulationRes { sim }` plus one system that steps the sim, calls `drain_events()` and writes `EventWrapper` messages, "the only point where the core simulation and Bevy synchronize." ([Bevy integration](https://andymai.github.io/elevator-core/bevy-integration.html))
2. **Gatebound**: three crates, `gatebound_domain`, `gatebound_sim` ("simulation rules and runtime state"), `gatebound_app` ("Bevy client"). [repo](https://github.com/Neoplayer/space). Bridge code not read.
3. **Middle ground**: iron-borders' `borders-core` "depends on Bevy's ECS rather than Bevy itself" ([Xevion](https://xevion.dev/projects/iron-borders), search snippet only).
4. **Rules inside ECS, turn-based**: Głowka (author inferred from domain): system order is "not exactly deterministic… especially painful in a turn-based game"; uses one-shot systems and queue resources ([blog](https://maciejglowka.com/blog/2024/turn-based-mechanics-with-bevys-one-shot-systems/)). Bevy issue #9635: JMS55 used "a manually coded action queue, and passing `&mut World` around manually"; rlidwka proposed a custom per-turn schedule ([#9635](https://github.com/bevyengine/bevy/issues/9635)).
5. **Headless card-game engines exist**: cardinal-kernel, "Headless, deterministic rules engine for turn-based, TCG-like games" ([crates.io](https://crates.io/crates/cardinal-kernel)); Bevy front end not checked.

**6. Catherine West, RustConf 2018** ([post](https://kyren.github.io/2018/09/14/rustconf-talk.html)): thesis "Rust highly rewards data-oriented design with simple, understandable ownership semantics." OO `Entity::update(&mut World)` double-borrows: "in rust the version of this is that you simply get a RefCell panic"; "Our 'OO-architecture' was a complete bust in Rust". Alternative: Vecs, indexes, generational indexes; "ECS is just SQL for games." Caveat: "I don't even think using some specific design pattern like an ECS is essential." LogLog later argued that "most people attribute as benefits of ECS are… benefits of generational arenas."

## Organizing rules for a Bevy front end
Agreed across sources: one plugin per feature/file (function plugins preferred); thin `main.rs` plus a library plugin so tests can use `MinimalPlugins`; gate systems with states and run conditions, and give each screen's entities `DespawnOnExit`; order writers before readers with `SystemSet`s across features; `impl Bundle` functions (BSN going forward) as entity templates; Messages for batched, schedule-ordered communication and observers for immediate reactions; SparseSet for frequently added/removed components (measure first).

Disputed: component size (Tainted Coders favors small, LogLog disagrees "in complete generality"); strictness of plugin isolation (Exofactory via Tainted Coders: no cross-plugin imports ever; bevy_new_2d nests plugins); events as the backbone (bevy_best_practices prefers events everywhere; Głowka moved to one-shot systems or observers for deterministic turn order); where the rules live (in ECS: Discussion #3370, Głowka; pure crate with a Bevy front end: elevator-core, Gatebound; West: ECS itself is optional).
