# Rust module and crate organization

Researcher report, session 00. Kept in full.

## Summary
Experienced Rust engineers treat the **crate** as the main architectural unit: a flat `crates/*` workspace under a virtual manifest for roughly 10k to 1M lines. Inside a crate, boundaries come from module privacy plus narrow `pub(...)`. Error types sit near the operations that produce them. The "god struct" problem is mostly a borrow-checker problem (`&mut self` locks the whole struct across a call). The usual fixes are sub-struct factoring, free functions over fields, view structs, or ECS-style plain data plus systems. On enforcement, only the compiler's visibility rules, Clippy `disallowed_*` combined with local `#[allow]`, dylint, cargo-modules and source-scanning tests reach below crate level. cargo-deny, `cargo metadata` tests, depgraph, machete/udeps, public-api and semver-checks work at crate granularity.

## Findings

### 1. matklad and rust-analyzer
1. **Flat workspace**: "for projects in between ten thousand and one million lines of code, the flat layout makes the most sense." The crate namespace is flat anyway: "It's not possible to write `hir::def` in Cargo.toml". "tree structure tends to deteriorate over time, while flat structure doesn't need maintenance." [Large Rust Workspaces](https://matklad.github.io/2021/08/22/large-rust-workspaces.html)
2. **Same post**: "Make the root of the workspace a virtual manifest"; folder name = crate name ("Don't succumb to the temptation to strip common prefix"); `version = "0.0.0"` for unpublished crates; publishable crates in `libs/`: "It makes it easier to check that things in `libs/` don't use things from `crates/`"; keep `src/` even for single-file crates; automate in Rust with `cargo xtask`.
3. **ARCHITECTURE.md**: "it takes 2x more time to write a patch if you are unfamiliar with the project, but it takes 10x more time to figure out *where* you should change the code." "Explicitly call-out architectural invariants. Often, important invariants are expressed as an *absence* of something"; "only specify things that are unlikely to frequently change." [ARCHITECTURE.md](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)
4. **Tests**: "large projects should have only one integration test crate with several modules" (`tests/it/main.rs`). For a published library he avoids unit tests and uses a single integration test, because it "forces the usage of the same public API that consumers use". "For an internal library, I avoid integration tests all together" (uses `src/tests.rs`). Prefer `#[cfg(test)] mod tests;` in a separate file so test-only edits don't recompile the lib; `doctest = false` for internal crates. Reports a 3x test-suite compile speedup in Cargo. [Delete Cargo Integration Tests](https://matklad.github.io/2021/02/27/delete-cargo-integration-tests.html)
5. **How to Test**: "focus on testing the features of the application, rather than on testing the code used to implement those features"; a single `check` function that "encapsulates API under test"; "good tests are not helpful for design in the small". [How to Test](https://matklad.github.io/2021/05/31/how-to-test.html)
6. **rust-analyzer architecture doc** (now `docs/book/src/contributing/architecture.md`, moved from `docs/dev/`): crates are labeled **API Boundary** or not (`syntax`, `hir`, `ide` are); `hir-*`: "these crates are not, and will never be, an api boundary." "`syntax` crate is completely independent from the rest of rust-analyzer. It knows nothing about salsa or LSP." "`base-db` knows nothing about cargo." "`rust-analyzer` is the only crate that knows about LSP and JSON serialization." `hir` "wraps ECS-style internal API into a more OO-flavored API". "all code invariants are tested by `#[test]` tests. There's no additional checks in CI, formatting and tidy tests are run with `cargo test`." "tests are data driven and do not test the API." [architecture.md](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/architecture.md)
7. **rust-analyzer tidy** (`xtask/src/tidy.rs`, `#[test] fn test() { Tidy {}.run(...) }`): reads source files and Cargo.tomls; panics on internal dev-deps with a version or internal deps without one, missing module docs, stray `should_panic`, trailing whitespace, license-set drift, and `lsp/ext.rs` changing without its doc hash. [tidy.rs](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/xtask/src/tidy.rs)
8. **rust-analyzer style guide on boundaries**: distinguishes internal changes, new `pub` items and new dependencies; "adding an innocent-looking `pub use` is a very simple way to break encapsulation"; "By default, avoid re-exports … for non-library code, re-exports introduce two ways to use something"; prefer `use crate::foo::bar` over `super::`; group imports by crate because that "allows spotting unwanted dependencies easier"; "Avoid making a lot of code type parametric, *especially* on the boundaries between crates." [style.md](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/style.md)

### 2. Visibility idioms
9. **Reference**: "By default, everything is *private*"; a private item "may be accessed by the current module and its descendants" (why a child `mod tests` can test private items). `pub(in path)` must name an ancestor; `pub(crate)`, `pub(super)`, `pub(self)` are shorthands; the restriction "only adds another restriction … To access an item, all of its parent items up to the current scope must still be visible". Facade by re-export: `pub use self::implementation::api;` with a private `mod implementation` makes `api::f` legal and `implementation::api::f` a privacy violation. [Reference: Visibility and privacy](https://doc.rust-lang.org/reference/visibility-and-privacy.html)
10. **`unreachable_pub`** "triggers for `pub` items not reachable from other crates"; rationale: the `pub` intent "can only be satisfied … if all items which contain this item are *also* publicly accessible … `pub(crate)` … more clearly expresses the intent". Allow-by-default; "Eventually … desired for this to become warn-by-default." Companion `unnameable_types` catches types you can obtain but not name. [rustc lints](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html)
11. **`mod.rs` vs `name.rs`**: "It is not allowed to have both `util.rs` and `util/mod.rs`." The `name.rs` form "is encouraged … as it is more consistent, and avoids having many files named `mod.rs`". [Reference: Modules](https://doc.rust-lang.org/reference/items/modules.html)

### 3. The god-struct problem
12. **Niko Matsakis, "Interprocedural conflicts" (2018)**: "we have a big struct that contains a number of fields, not all of which are used by all the methods"; the compiler "only examines one function at a time". Four workarounds: inline (not DRY); factor a sub-struct ("doesn't always work" when fields don't factor nicely); free functions over individual fields ("a significant ergonomic regression"); view structs of references ("fairly heavy weight"). [baby steps](https://smallcultfollowing.com/babysteps/blog/2018/11/01/after-nll-interprocedural-conflicts/)
13. **View types (2021, revisited 2025)**: `{f1, f2} T` restricts accessible fields; "This is not a proposal (yet?)"; per-function checking "gives room for other functions to change, so long as they don't change their signature"; 2025: "'aggregate' types like Data present a composition hazard". Not in the language. [2021](https://smallcultfollowing.com/babysteps/blog/2021/11/05/view-types/), [2025](https://smallcultfollowing.com/babysteps/blog/2025/02/25/view-types-redux/)
14. **Disjoint field borrows within one body**: borrowck "does understand structs sufficiently to know that it's possible to borrow disjoint fields of a struct simultaneously" but "doesn't understand arrays or slices". [Rustonomicon: Splitting Borrows](https://doc.rust-lang.org/nomicon/borrow-splitting.html)
15. **Catherine West (kyren), RustConf 2018**: she does **not** condemn the big struct. Her target is OO encapsulation. She endorses a "giant nested tree of entirely public structs" with systems as plain functions taking `&mut game_state`, because "Rust is rather good at letting you split borrows for different fields of a public struct". On OO entities: "the more modules we add inside our entities to help reuse code, the more layers are added". ECS then answers the remaining problem: "every 'system' … depends on *all* of the types that go into our game state". "if you forget OO design and instead just concentrate on the data representation of your game state…". [kyren.github.io](https://kyren.github.io/2018/09/14/rustconf-talk.html)

### 4. When to split a module into a crate
16. **Compile-time parallelism needs a wide graph**: "crates form a directed acyclic graph"; "split the code into crates": "It is not *that* easy" (a linear chain gains little); aim for "a common vocabulary crate, a number of independent features, and a leaf crate". "The most important property of a crate is which crates it doesn't (transitively) depend on." "keep serialization at the boundary of the system, in the leaf crates." Cost: "generics in Rust can lead to accidentally-quadratic compilation times across many crates". [Fast Rust Builds](https://matklad.github.io/2021/09/04/fast-rust-builds.html)
17. **Inlining**: "In Rust, a unit of (separate) compilation is a crate … Without `#[inline]`, even the most trivial of functions can't be inlined across the crate boundary." [Inline In Rust](https://matklad.github.io/2021/07/09/inline-in-rust.html). Partly outdated: Rust 1.75 "Automatically enable cross-crate inlining for small functions" ([releases.rs 1.75](https://releases.rs/docs/1.75.0/), PR #116505).
18. **Coherence constraints**: inherent impls: "An implementing type must be defined within the same crate as the original type definition." Orphan rule: a trait impl "is only allowed if either the trait or at least one of the types in the implementation is defined in the current crate." So splitting moves every `impl Foo {}` with `Foo`'s crate, and foreign-trait impls must sit next to the type or the trait. [Reference: Implementations](https://doc.rust-lang.org/reference/items/implementations.html)
19. **Other costs/benefits (from memory, unverified)**: Cargo rejects cyclic crate dependencies (dev-dependency cycles allowed); items used by a sibling crate must become `pub`, widening the API; generic code is monomorphized per consuming crate.

### 5. Error type organization
20. **Sabrina Jewson, "Modular Errors in Rust"**: "error types should be located near to their unit of fallibility." Against a crate-wide error as the default: "it's certainly not *the library itself*"; "the `unicode_blocks::Error` type is inherently misguided". Problems with the "big `#[non_exhaustive] enum`": frozen variant fields, no private enum fields, non-modularity: "Every API is interconnected with each other through the underlying error type". Argues against `From` conversions that silently narrow meaning; would not use thiserror for a library. [sabrinajewson.org](https://sabrinajewson.org/blog/errors)
21. **dtolnay**: "Use Anyhow if you don't care what error type your functions return … common in application code. Use thiserror if you are a library that wants to design your own dedicated error type(s)." [anyhow README](https://github.com/dtolnay/anyhow). thiserror docs recommend an opaque public struct over a private `ErrorRepr` enum, "able to evolve without breaking the crate's public API". [thiserror docs](https://docs.rs/thiserror/latest/thiserror/)
22. **matklad on `std::io::Error`**: private repr plus public `#[non_exhaustive]` fieldless `ErrorKind`; "publicly exposing `ErrorKind` is much less scary". [Study of std::io::Error](https://matklad.github.io/2020/10/15/study-of-std-io-error.html). rust-analyzer's rule: "core parts … can't fail", returning `(T, Vec<Error>)`.

## Rust-specific facts that change where code goes
1. The crate is the unit of compilation, inlining, coherence and acyclicity. Cargo forbids crate cycles (from memory, finding 19); modules inside a crate may depend on each other cyclically. A cross-crate split costs inlining (eased since 1.75) and duplicated generic instantiation.
2. Inherent impls must live in the type's crate, and the orphan rule ties trait impls to the trait's or the type's crate, so "behavior next to its data" is forced at crate level. Within a crate, `impl` blocks can sit in any module.
3. Privacy is module-tree based: descendants see ancestors' private items (tests go in a child `mod tests`); `pub(in path)` names ancestors only; `pub` deep inside a private module is not public, which is why `unreachable_pub` exists.
4. `&mut self` borrows the whole struct across a function boundary; disjoint field borrows work only within one body. Large shared state therefore pushes toward sub-structs, free functions over fields, view structs or ECS, which makes data layout an architectural decision, not only an encapsulation one.
5. Integration tests in `tests/` are separate crates that see only the `pub` API, and each file links a separate binary. That shapes the choice between testing through the public API and keeping tests in `src/`.
6. No built-in module-level dependency rule. Inside a crate, enforce with visibility, Clippy `disallowed_*` plus `#[allow]`, dylint or textual tests; across crates, the Cargo graph itself enforces.
