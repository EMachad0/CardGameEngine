# Trait impl placement: official and semi-official sources

Researcher report, outside a session, for PR #70's doc gaps, kept in full. Question: where in a
crate a trait `impl` goes, according to official and semi-official Rust sources.

## Summary
None of the official or semi-official Rust sources I checked says which module or file a trait `impl` should go in. The language only requires the impl to be in the right crate (the orphan rule), and the module that holds a trait impl has no effect on who can use it. A trait impl gets no visibility from its module, and `pub impl` is rejected with error E0449. Under RFC 2145, an impl is exactly as visible as the least visible of its trait, its self type and its type parameters. Placement is therefore purely a style choice. The only hard constraint inside a crate is that the impl has to be written somewhere that can name every type and trait it mentions. std places trait impls in several ways: next to the type, next to the trait, in separate per-trait files, and even inside private `mod imp` blocks.

## Findings
1. **Reference, Implementations: crate-level rules only, no module rule.** Verified quote for inherent impls: "A type can also have multiple inherent implementations. An implementing type must be defined within the same crate as the original type definition." Its own example puts an inherent `impl Color` inside a different module (`mod values`) and notes: "Impl blocks in different modules are still accessed through a path to the type." On the orphan rule (verified): "a trait implementation is only allowed if either the trait or at least one of the types in the implementation is defined in the current crate." The page never uses the word "visib…" and says nothing about which module an impl should go in. [Reference: Implementations](https://doc.rust-lang.org/reference/items/implementations.html)
2. **Reference, Visibility and privacy: says nothing about impls.** It covers item privacy, `pub(in path)` and re-exports, but impl blocks don't appear in it. The closest it gets (verified): "Associated items in a `pub` Trait are public by default." [Reference: Visibility](https://doc.rust-lang.org/reference/visibility-and-privacy.html)
3. **Impls cannot carry a visibility qualifier.** Error E0449 (verified): "Visibility qualifiers are not permitted on enum variants, trait items, impl blocks, and extern blocks, as they already share the visibility of the parent item." Its example comments say (verified): "Trait methods share the visibility of the trait, so `pub` is not allowed in either case." [E0449](https://doc.rust-lang.org/error_codes/E0449.html)
4. **RFC 2145 (type privacy) is the normative answer to "can a module hide or narrow a trait impl?" The answer is no.** An impl is "private" only because of what it names, not where it is written. Verified quotes:
   - "When associated function is defined in a private impl (i.e. the impl type or trait is private) it's guaranteed that the function can't be used outside of the impl's area of visibility."
   - "type privacy additionally prohibits use of any associated items from private impls."
   - Trait methods follow `vis(<Type as Trait>::foo) = min(…vis(Type), vis(Trait))`.

   Jack Wrenn's blog post summarises it this way (verified, semi-official commentary): "the `impl` keyword doesn't have an associated visibility; there's no such thing as `pub impl`… a trait implementation is as visible as the *least* visible of its trait, target type, or type parameters." [RFC 2145](https://rust-lang.github.io/rfcs/2145-type-privacy.html) · [Wrenn, Scoped Trait Implementations](https://jack.wrenn.fyi/blog/private-trait-impls/)
5. **Scoped or hidden impls were proposed and postponed.** RFC PR #2529, "Hidden trait implementations" (Centril), would have allowed `crate impl Copy for Foo {}` while keeping the impl "public wrt. coherence and overlap". It was closed with the labels postponed and finished-final-comment-period (2021-03-27). scottmcm wrote (verified): "the kind of big idea that's not a good fit for the current roadmap cycle". Graydon's comment on the PR explains why impls are global (verified): "the ship sailed: reasoning about the impl relation is global. Starting to invent secondary ways of making it non-global in addition to the visibility rules around the traits and types involved in the relation seems to me like inviting more confusion". The same thread raises the problem that specialization combined with scoped impls would break coherence. [rfcs#2529](https://github.com/rust-lang/rfcs/pull/2529)
6. **The Rust Book explains the orphan rule but not module placement.** Verified quote from ch10-02: "we can implement a trait on a type only if either the trait or the type, or both, are local to our crate… This restriction is part of a property called *coherence*, and more specifically the *orphan rule*." The module chapters (ch07-03 and ch07-05) never mention where impls should go. ch07-05 contains no "impl" at all, and ch07-03 only shows an inherent impl placed next to its struct. [Book ch10-02](https://doc.rust-lang.org/book/ch10-02-traits.html) · [ch07-05](https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html)
7. **Rust API Guidelines (C-COMMON-TRAITS) work at crate level only.** Verified quote: "Rust's trait system does not allow *orphans*: roughly, every `impl` must live either in the crate that defines the trait or the implementing type. Consequently, crates that define new types should eagerly implement all applicable, common traits." The Interoperability page never mentions modules. [API Guidelines: Interoperability](https://rust-lang.github.io/api-guidelines/interoperability.html)
8. **The Rust Style Guide covers formatting and imports, not impl ordering or placement.** Verified: "`use` statements, and module *declarations*… must come before other items." The "Impls" section only covers how an impl is formatted (block indent, breaking before `for`). [Style Guide: Items](https://doc.rust-lang.org/style-guide/items.html)
9. **rust-analyzer's style guide orders items within a file but says nothing about which module.** Verified quotes: "Optimize for the reader who sees the file for the first time", "If there's a mixture of private and public items, put public items first. Put `struct`s and `enum`s first, functions and impls last. Order type declarations in top-down manner." Its example puts `impl Parent {}` and `impl Child {}` after both structs. It also says to import `std::fmt`/`std::ops` and write `impl fmt::Display for …` because this "Makes it clear that a trait is implemented, rather than used." [rust-analyzer style.md](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/style.md)
10. **The std-dev-guide and rustc-dev-guide say nothing about placement.** The std-dev-guide covers whether new trait impls break things (inference, deref coercion) and requires an FCP for new impls of stable traits. Its only placement-like rule is about deprecated items, which "should be moved to the bottom of the module or `impl` block" (verified). The rustc-dev-guide coherence chapter covers the overlap and orphan checks and nothing about modules. [Maintaining std](https://std-dev-guide.rust-lang.org/maintaining-std.html) · [rustc-dev-guide: Coherence](https://rustc-dev-guide.rust-lang.org/coherence.html)
11. **What std actually does (I looked at the source; there is no written policy).**
    - `library/alloc/src/vec/partial_eq.rs` is a file in `Vec`'s module that holds only `PartialEq` impls. This is placement by type, split out by trait.
    - `library/core/src/fmt/num.rs` puts `impl fmt::Display for u128`/`i128` in the *trait's* module. It also generates the Display impls for the other integer types inside private `mod imp { … }` blocks, yet those impls are publicly usable. That is concrete evidence that the containing module's privacy doesn't matter.

    [vec/partial_eq.rs](https://raw.githubusercontent.com/rust-lang/rust/master/library/alloc/src/vec/partial_eq.rs) · [fmt/num.rs](https://raw.githubusercontent.com/rust-lang/rust/master/library/core/src/fmt/num.rs)
12. **Clippy has no lint about where trait impls go.** `multiple_inherent_impl` is in the restriction group and allow-by-default. Verified: "Checks for multiple inherent implementations of a struct… allowing values of `module`…, `file`…, or `crate` (anywhere in the crate, default)". Rationale: "Splitting the implementation of a type makes the code harder to navigate." The config option is `inherent-impl-lint-scope`. The lint covers **inherent** impls only. I found no lint that checks trait impls placed away from the type or the trait. The only nearby trait-impl lints (`same_name_method`, `should_implement_trait`) don't concern placement. [Clippy lints](https://rust-lang.github.io/rust-clippy/master/index.html#multiple_inherent_impl)
13. **rustdoc shows impls on the type's page wherever they are written (supported by sources, not by an explicit statement).** The rustdoc book (verified): "the page lists associated functions and trait implementations, including automatic and blanket implementations". rustdoc's internal `collect_trait_impls` pass (verified): "Collects trait impls for each item in the crate." Neither says "regardless of module" in so many words. The `mod imp` example in finding 11 is consistent with that behaviour: `u8`'s docs page lists `Display`. [How to read rustdoc](https://doc.rust-lang.org/rustdoc/how-to-read-rustdoc.html) · [collect_trait_impls](https://doc.rust-lang.org/stable/nightly-rustc/rustdoc/passes/collect_trait_impls/index.html)

**How this applies to your four cases.** This part is my inference from findings 1–4. The language allows every placement in the crate, as long as the impl's module can name everything the impl mentions.
- **(a) Local trait for a local type in another module:** any module can hold it. Common practice puts it with the type or with the trait.
- **(b) `From<A> for B`, with `A` private:** the impl has to sit in `A`'s module or a descendant, since that's where `A` can be named. Under RFC 2145 the impl is effectively private wherever it is written, so putting it in `B`'s file isn't possible anyway.
- **(c) Local trait for a foreign type:** the type's file isn't yours, so the trait's module is the natural home. std does this in `fmt/num.rs`.
- **(d) `Default` for a local type, placed in a third module:** this compiles, and the impl is still global and appears on the type's docs page. The only cost is that it's harder to find.

A defensible rule: put the impl with the type by default; with the trait when the type is foreign; and in the narrowest module that can name every type it involves when privacy forces that.

## Gaps
- I didn't find any official text saying "rustdoc shows impls regardless of the defining module". That is inferred from the pass description and std's `mod imp` example. Running `cargo doc` on a small crate with an impl in a private third module would confirm it.
- The current Reference has no section on type privacy. RFC 2145 is the normative text, and I didn't check whether the Reference has absorbed it elsewhere (for example under "names" or "privacy" sections added since).
- I searched Clippy's lint list for inherent and trait-impl lints but didn't read all 841 lints. No placement lint for trait impls turned up.
- I didn't read the full RFC 2529 text, only the PR summary and comments.
