## Summary
The ocap literature answers questions 1 and 2. Miller's own texts define how references are obtained, separate permission from authority, state POLA, and say that a reference to an object allows calling any of its operations, so narrower access needs a separate facet or forwarding object. On the Rust side, privacy is granted per module and descendants, and `&mut T` is described as exclusive access. For question 4, Niko Matsakis's "view types" post names the exact tension, and Bevy's `SystemParam` is a working example of narrow lending.

## Findings
1. **Four ways to get a reference.** "Only Connectivity Begets Connectivity. Consider all the ways Bob can obtain access to Carol. Only four possibilities are allowed": Introduction ("Somebody sends Bob a reference to Carol"), Parenthood ("If Bob already exists and Carol does not, Bob may create Carol"), Endowment ("Bob is born holding a reference to Carol"), Initial Conditions ("Bob and Carol may both already exist and already be connected in this earliest state"). [erights.org, From Objects to Capabilities](http://www.erights.org/elib/capability/ode/ode-capabilities.html). The thesis has matching sections 9.2.1 to 9.2.5 with the same titles. [Thesis TOC](http://www.erights.org/talks/thesis/markm-thesis.pdf)
2. **Encapsulation still holds when you have a reference.** "From outside an object, one must not be able to gain access to the object's internals without the object's consent, even if one has a reference to the object." [Same page](http://www.erights.org/elib/capability/ode/ode-capabilities.html)
3. **Permission vs authority.** "Whether to enable cooperation or to limit vulnerability, we care about authority rather than permissions. Permissions determine what actions an individual program may perform on objects it can directly access. Authority describes effects a program may cause on objects it can access, either directly by permission, or indirectly by permitted interactions with other programs." [Miller & Shapiro, Paradigm Regained (2003)](http://www.erights.org/talks/asian03/paradigm-revised.pdf). The thesis "borrows liberally" from this paper (MS03), and its section 8.1 is titled "Permission and Authority". [Thesis](http://www.erights.org/talks/thesis/markm-thesis.pdf)
4. **POLA (thesis section 3.1).** "The Principle of Least Authority (POLA) recommends that you grant each program only the authority it needs to do its job" and "we must provide the right amount of authority just-in-time, not excess authority just-in-case." [Robust Composition](https://papers.agoric.com/assets/pdf/papers/robust-composition.pdf)
5. **A reference grants every operation; narrowing means a facet.** "Alice has direct access to /etc/passwd, so she has permission to invoke any of its operations." Also: "we model restricted access to an object, such as read-only access to /etc/passwd, as simple access to another object whose behavior embodies the restriction, such as access to the read-only facet of /etc/passwd which responds only to queries." [Paradigm Regained](http://www.erights.org/talks/asian03/paradigm-final.pdf)
6. **Attenuation (thesis section 2.2).** "programmers control access partially by manipulating the access graph, and partially by writing programs whose behavior attenuates the authority that flows through them... the access abstraction consists of objects which forward some messages from Bob to Carol." [Thesis](http://www.erights.org/talks/thesis/markm-thesis.pdf)
7. **Rust privacy is per module.** The Rust Reference says: "If an item is private, it may be accessed by the current module and its descendants." It also says a child `mod test` "could access any items of the parent module through the second case." [Rust Reference, Visibility and privacy](https://doc.rust-lang.org/reference/visibility-and-privacy.html). *Inference:* the scope is a module subtree. It is not one object or one function, so every function in the holder's module can touch the private fields of every instance.
8. **`&mut T` as an access right.** Felix Klock (Rust compiler team) lists "Exclusive access: `&mut T`" and says "A `&mut T` provides *temporary* exclusive access; even the original owner cannot mutate the object while you have the reference." Elsewhere the same talk says "shared state (R/W-capabilities controlled via types)". [Aliasing, Capabilities, and Ownership in Rust (IWACO 2017)](https://pnkfx.org/presentations/iwaco-2017.html)
9. **Owned handles as capabilities.** cap-std: "Capability-based security seeks to avoid ambient authority... To open a file, one needs a `Dir`". [cap-std README](https://github.com/bytecodealliance/cap-std/blob/main/README.md)
10. **The tension, named directly.** Matsakis on `&mut self` lending the whole struct: "Traditional privacy (`pub` fields and so on) is like a view type in that, if you are outside the module, you can't access private fields. *Unlike* a view, though, you can call methods on the type that *do* access those fields. In other words, traditional privacy denies you *direct* access, but permits *intermediated* access." His workaround: "I introduced the [`cfg`] field of the MIR `Builder` type to resolve errors where some methods only accessed a subset of fields." [View types for Rust](https://smallcultfollowing.com/babysteps/blog/2021/11/05/view-types/). *Inference:* this is the learner's `&mut Zones` case. Privacy limits who can see the fields. Whoever holds `&mut` gets every visible method, which is Miller's permission vs authority split.
11. **Splitting borrows.** Rust's borrow checker "does understand structs sufficiently to know that it's possible to borrow disjoint fields of a struct simultaneously." [Rustonomicon](https://doc.rust-lang.org/nomicon/borrow-splitting.html). *Inference:* the holder's module can split `&mut self` into per-owner `&mut` borrows and pass each one to a step function in another module. That function gets access to one sub-owner, not the whole holder.
12. **Bevy as narrow lending.** Bevy systems declare parameters such as `Res<'w, SomeResource>` and `ResMut<'w, SomeOtherResource>` instead of the whole `World`. The `SystemParam` trait has an `init_access` method. [Bevy SystemParam docs](https://docs.rs/bevy/latest/bevy/ecs/system/trait.SystemParam.html). *Inference:* each system gets a narrowed view of `World` (a facet) instead of `&mut World`.
